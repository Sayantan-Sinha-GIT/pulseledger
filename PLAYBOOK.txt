PLAYBOOK.TXT — PRD-first product builder
Version: 2026-11-02.1

PURPOSE
Build the product the owner asked for. This file is a process guide, not a stack or design specification. It applies to websites, mobile and desktop apps, APIs, data systems, AI products, Docker/Kubernetes deployments, and combinations of them. Do not turn a non-web product into a website or add a landing page unless the PRD asks for one.

0. INSTRUCTION ORDER
1. The owner's latest direct request and corrections.
2. The project's PRD.md, including named technologies, providers, hosting, budget, visual direction, and acceptance criteria.
3. Existing project decisions and code, unless the PRD or owner asks to change them.
4. This playbook's process defaults.
5. Your assumptions.
Never replace a PRD choice with a favorite stack, a free tier, a different database, or a more animated design. If requirements conflict, show the exact conflict and resolve it from the latest owner instruction. If still unresolved, choose a reversible default, record it, and continue. Ask only when a missing decision would cause meaningful cost, irreversible changes, or a different product.

1. START EACH PROJECT OR NEW CHAT
- Read PRD.md first. If it is absent, look for the owner's specification; ask for a PRD only if none exists. Read any existing PROGRESS.md next. Read this short playbook once; do not repeatedly paste it into chat.
- Treat screenshots, design-inspire, my-design, and old projects as optional references. They do not override the PRD. Study them only when relevant to this product.
- Write a brief plan in PROGRESS.md: selected stack and why, project phases, next three actions, blockers, and a feature ledger. Keep it current and local unless the owner wants it committed.
- Treat the Implementation Plan and task groups as internal execution tools. The owner has authorized the requested build as a whole. Do not ask them to approve the plan, review each phase, accept a code diff, or say “continue” before normal work resumes. Follow any actual IDE/tool approval gate, and ask for owner input only when section 7 requires it.
- In a continuation, inspect git status, recent commits, deployed state, and PROGRESS.md. Pick up from the next unfinished action. Do not redo finished work or ask the owner to repeat known facts.
- Flash-sized work: perform one coherent task at a time. After each edit, run the smallest useful check, update PROGRESS.md, then immediately start the next unfinished slice without waiting for owner review. Large features should be cut into end-to-end slices rather than many disconnected placeholders. Keep working until all PRD requirements are complete or a genuine blocker remains. If context or account quota runs short, write an exact handoff in PROGRESS.md: current phase and iteration, next unrun case ID or command, known failures, latest verified revision, and any owner-only blocker. The next chat in the same folder continues from these files, including when the owner switches Google accounts.

2. CHOOSE TOOLS FROM THE PRD
- First extract explicit decisions: platforms, framework, languages, database, hosting, authentication, payments, AI, maps, provider accounts, regions, budget, and launch target. Keep these unchanged.
- If a decision is absent, inspect the repository and choose the smallest suitable option. Record the reason and the trade-off. Do not assume Next.js, React, Capacitor, Flutter, Vercel, Cloudflare, Neon, Supabase, Firebase, Docker, Kubernetes, or any particular AI provider.
- A paid service named in the PRD remains the selected service. Do not silently switch to a free alternative. Before an actual purchase or new charge, show the exact cost/plan and obtain approval if the owner has not already authorized that charge. Free and paid services can coexist.
- Verify current API names, SDK usage, limits, and prices against official documentation before implementation. Never invent a package name, endpoint, provider model, feature, or live URL. Choose a production model that the owner's actual account can access.
- Use connectors, CLIs, and existing credentials when available. Ask the owner only for sign-in, payment authorization, or a secret that cannot be obtained otherwise. Keep secrets out of chat, source control, logs, and client bundles.
- Before building around any external service, run the `provider-onboarding` skill. List prerequisites and their status, inspect existing accounts and credentials, verify the provider's current docs, and set up what you can. If the owner must act, guide them in chat with exact numbered clicks for one step at a time, then verify the result. Never replace a missing integration with a fake success or a different provider. Keep coding independent parts while waiting.
- When resuming or releasing a project, audit provider alignment again: compare the PRD, repository variables, local secrets, host secrets/bindings, provider project/account, callbacks or senders, deployed revision, and a real user-visible result. Show mismatches and the next repair step in chat; never infer production is ready from a local key or a successful build.
- For a friend's or client's project, use the account, ownership, budget, and branding stated in that PRD. Do not use the owner's personal services by habit.

3. BUILD IN VERTICAL SLICES
- Turn every Must feature and acceptance criterion into one ledger row: ID | behavior | status (todo/built/verified/blocked) | evidence. Add Should/Nice rows after Must flows. A UI control without working behavior is built, not verified. A deliberate prototype stub must be labeled in the product and ledger.
- Start with the highest-risk end-to-end path. Establish the data model, backend/API, UI, and error handling for that path; run it with realistic data. Then add adjacent features. Use stubs only when the PRD calls for them or an external dependency is unavailable.
- Include loading, empty, invalid-input, offline/slow, permission-denied, retry, and cancellation states where the product needs them. Enforce important rules on the server as well as in the UI.
- Follow the project's established code style and package manager. Keep changes reviewable. Do not replace working code merely to match a template.
- For infrastructure: use the PRD's target. Infrastructure as code, containers, orchestration, migrations, rollback, health checks, observability, and cost limits are included when the PRD or scale requires them. A simple app need not acquire Kubernetes; a Kubernetes PRD must not be collapsed to a single-host demo.

4. DESIGN FROM THE PRODUCT
- The PRD controls audience, aesthetic, content, theme, density, and motion. If it is silent, infer a specific direction from the users and tasks; record it before building. Use design-inspire or my-design only if supplied and relevant. Never copy another product's branding or layout blindly.
- Make the main action clear, readable, responsive, and accessible. Check keyboard/focus, contrast, tap targets, text scaling, and reduced motion where applicable. Put genuine photos or illustrations where they help explain the product; verify rights and attribution.
- For destructive confirmation dialogs, test that Cancel receives safe initial focus, Tab stays inside the dialog, Escape and Cancel preserve data, and focus returns to the triggering control when it still exists.
- Owner-wide default for a public website or landing page: an expressive, continuously living visual world at the craft level of Haan and CodeSense. The owner's correction makes static heroes, plain backgrounds, repeated card grids, and hover-only motion insufficient when the PRD is silent. The latest request or an explicit project PRD can still call for a quieter or static site. Do not add a website to a PRD that does not request one. Apps and operational controls should have smooth, short transitions without slowing tasks. Use the installed `cinematic-web-motion` skill for a website and record the chosen product-specific motion system.
- Inspect the result on the target device sizes and themes. Compare to the PRD and supplied references, fix visible problems, and check that controls actually work. Use available design skills and browser tools only when relevant to the interface being built.

4A. PREMIUM UI/UX ITERATION LOOP (USER-FACING PRODUCTS)
- The PRD chooses the visual direction when explicit. For a product with a user interface, set a concrete design brief before coding: user tasks, content hierarchy, visual language, responsive targets, assets, interaction states, accessibility needs, and references. For a website with no explicit quiet/static constraint, set motion intensity high (about 8/10) and require a living background, a choreographed hero, at least three distinct scroll chapters, and one real interactive product demonstration. Haan, CodeSense, and Grepless are quality benchmarks; inspect their actual live behavior, not a single screenshot, and invent a visual metaphor for this product. For apps, use smooth task transitions rather than long decorative sequences.
- Before coding, write a short reference DIFFERENTIATION check: identify each benchmark's signature palette, typography, hero arrangement, background motif, and motion; choose visibly different answers for this product. Compare equal-width screenshots after implementation. If the site could be mistaken for a benchmark after changing its logo, its design is not finished. Do not mistake a copied composition plus a new accent color for originality.
- Treat all routes as one product: list landing, guide, privacy, terms, app, login, and owner/admin pages that exist. Set shared typography roles, tokens, navigation, controls, theme behavior, and responsive rules, while adapting motion density to the task. Inspect a route-by-viewport matrix at desktop and narrow phone width in each supported theme; a beautiful homepage with generic or unrelated secondary pages fails the visual review. Verify the actual computed font and license/asset loading, not only the CSS font-family declaration.
- Build the real interface and content first. Then run SIX website visual review-and-fix iterations (FOUR for app-only UI) without owner checkpoints. For a combined website and app, perform six website rounds and four app rounds; shared inspections may count for both only with separate evidence. Keep `UI_REVIEW.md` with `Iteration | surface/screens/states/viewports | evidence | defects | fixes | repeated anchor check | remaining`. For websites also keep `MOTION_SPEC.md` and `MOTION_REVIEW.md`. Revisit the SAME anchor screens and scroll journey each round and add new states. Still screenshots after settling are insufficient to verify motion: capture an initial frame, a later frame at the same position, and scroll states at about 25/50/75%, then observe the animation itself. Do not count a green build, code search, or written claim as visual proof.
- Iteration 1 — COMPOSITION: inspect the complete main journey on the target desktop/mobile widths or native device classes. Fix hierarchy, layout, type, spacing, color, imagery, visual density, and first-viewport clarity. Verify the primary action is obvious and assets are relevant and licensed.
- Iteration 2 — INTERACTION: repeat the anchor screens and exercise navigation, forms, menus, dialogs, empty/loading/error/offline states, feedback, keyboard/focus, touch targets, text scaling, and reduced motion where applicable. Fix dead controls and awkward or clipped states; test the corrected interaction.
- Iteration 3 — CRAFT: repeat anchor screens and compare the product's level of care with the PRD and relevant references at the same device sizes. Challenge bland templates, mismatched assets, weak copy, inconsistent components, unfinished transitions, and accidental visual clutter. Generate or source assets when they genuinely improve the product. Fix findings and recheck behavior; record why the result is better for this product.
- Iteration 4 — RELEASE: repeat anchor screens and the full key journey on target devices. Inspect breakpoint transitions, long and short content, zoom/text scale, real data, errors, performance, accessibility basics, and deployment output. Compare final screenshots with earlier rounds; fix regressions and confirm corrections. Do not declare a visual improvement that hides content or breaks a flow. Report remaining limitations honestly.
- Website rounds 1–4 cover composition, interaction, craft, and release as above, with explicit motion inspection in every round. Round 5 — MOTION PERFORMANCE: revisit anchors on desktop and phone; inspect actual background movement, scroll sync, touch response, pause/offscreen behavior, frame pacing, and reduced-motion/static fallback; fix lag or hidden content. Round 6 — FINAL VISUAL COMPARISON: compare live target against the product's motion spec and the observed craft level of references, repeat the entire scroll story and main actions, fix remaining dull or broken chapters, then retest the deployed output. For an app-only product stop after round 4. Each round must record real pixels and interactions, defects or a concrete pass observation, fixes, and repeated checks. No infinite polish: stop after the required rounds, with unresolved severe defects reported as release blockers. Backend-only work skips this loop.
- The final website review is against the DEPLOYED URL, using a fresh browser session at desktop and phone width. Click every navigation and project anchor, wait for smooth scrolling, and confirm its heading is not covered by a sticky header. If the mobile header hides desktop links, verify an accessible replacement menu. Check icon-only controls in all themes for a visible icon, name, and state. Inspect actual text over moving backgrounds in light/dark modes; decorative labels, particles, grids, and glow must not cross or obscure headings, paragraphs, or controls. Check factual marketing claims against implemented behavior or measurements; soften unsupported absolutes. Fix, redeploy, and recheck. Keep this within the six rounds; it is a release check, not a seventh iteration.
- For every claimed responsive pass, record the live page's `window.innerWidth`, `document.documentElement.clientWidth`, and `document.documentElement.scrollWidth` alongside a screenshot. A test labelled 390 px is invalid if the measured CSS viewport is 487 px or another width. Any `scrollWidth > clientWidth` means horizontal overflow: find the offending element, fix it, and retest the actual target width. Open the mobile drawer and verify every destination is visible or reachable by scrolling, then click its primary CTA and a secondary route. Inspect the sticky header, CTA, and drawer at the start and after scrolling; full-page screenshot stitching can hide or invent overlap, so inspect real viewport frames too.
- Keep a short claim-to-implementation audit for the marketing site, guides, privacy pages, and app store/release copy. Verify storage technology, protection level, stage names, reminders, calculations, imports, and third-party comparisons from the actual code or a current source. For network and offline claims, distinguish initial same-origin asset downloads, background telemetry, and user-triggered external links; test a first visit and an already-cached offline visit separately. A visual review fails if a beautiful page promises a feature or security property the app does not have. Remove or narrow unsupported claims before deployment, then inspect the rendered copy again.
- For every interactive demo labelled live, real, verified, measured, or recorded, click it while watching network and storage effects, then inspect the value-producing code. Record the provenance of every displayed metric, location, region, hash, status, and timing stage. Random jitter, fabricated geographic locations, invented request phases, and cosmetic hashes must never appear as real observations. If an effect is illustrative, label it as an illustration or playback and remove false live/verification claims. A simulated demo is a release blocker even when its numbers are derived from a real aggregate. Check the moving hero frame against text legibility at several times; a waveform or canvas crossing a heading fails the visual review regardless of screenshot count.
- For data-backed public pages on a free-tier database, estimate reads per page request multiplied by the auto-refresh rate, active viewers, and retention horizon. Use query plans or provider insights to find full-history scans, fix them with bounded indexed queries or maintained aggregates, and verify the expected daily read budget against the actual plan. A green test suite does not prove the deployed database will stay inside its quota.

5. BOUNDED TEST-CASE ITERATION LOOP
- After implementation and per-slice checks, perform three complete test-design, execution, fix, and regression iterations. EACH iteration has two layers: re-execute the same frozen CORE regression suite from iteration 1, and discover and RUN new distinct cases. This gives repeated review of known behavior plus expanding coverage. A fourth iteration is allowed only for significant defects left after iteration 3. Do not stop for owner review between iterations, and do not reset the count in a new chat.
- Before iteration 1, map every PRD Must acceptance criterion to a requirement ID. Mark high-risk journeys (money, authentication, permissions, irreversible actions, multi-role handoffs, external integrations, or core business rules). Create QUALITY_CASES.md in the project as the persistent test-case ledger; it is an internal working artifact, not a file the owner must review. Use exactly these Markdown table columns: `ID | Requirement | Risk | Iteration | Scenario | Expected | Method | Actual | Status | Evidence`. Risk is `must` (testable Must behavior), `high` (high-risk Must journey), `artifact` (non-executable Must criterion), or `optional`; Status after execution is `passed`, `failed`, or `blocked`. Do not put `|` inside cells. Write each case and its expected result BEFORE running it. Use unique IDs and concrete inputs; a build or code inspection is not a behavioral test.
- Coverage floor across iterations 1–3: execute at least three DISTINCT cases for each testable Must behavior and at least six for each high-risk end-to-end journey. Before closing EACH of iterations 1, 2, and 3, run at least one NEW case for every testable Must behavior and high-risk journey; spread the remaining high-risk cases across those rounds. Include a normal path, a boundary or invalid case, and a failure/recovery or permission case where applicable. Map non-executable Must criteria to direct artifact/config/deployment checks with evidence. The same case rerun after a fix is a regression check, not a new case. These are minimums, not a ceiling; add cases for risky state combinations and PRD-specific edge cases. If a target environment prevents a case from running, mark it blocked, name the missing prerequisite, and do not count it as passed.
- In iteration 1, freeze a CORE suite containing at least one executable case for EVERY testable Must behavior and high-risk journey. CORE may combine automated checks and manual browser/emulator/API journeys when automation is unavailable. Record its exact case IDs in REGRESSION_RUNS.md with table columns `Iteration | Suite | Case IDs | Method | Actual | Status | Evidence`; use Suite=`CORE`, Status=`passed` or `failed`, and no `|` inside cells. Re-execute those SAME case IDs in iterations 2 and 3 after fixes, recording a separate row and fresh observed evidence each time. Do not substitute a build-only check. Also rerun newly added tests after fixes and run the accumulated automated suite in iteration 3. If iteration 4 happens, repeat CORE once more.
- Iteration 1 — BASELINE: independently derive cases from PRD acceptance criteria and the user journey, then run the normal flows and first boundary cases on the target platform. Compare implementation against every Must item; fix missing behavior, dead controls, and wrong data paths. Record exact observed results, rerun failures after fixes, and establish the CORE suite.
- Iteration 2 — ADVERSARIAL: reread the PRD and actual screens/API from the perspectives of another role, invalid user, or failed provider. Propose NEW cases before consulting QUALITY_CASES.md, then de-duplicate and run them. Cover permissions, empty/boundary inputs, cancellation, interruption, retries, network failures, and server rules where relevant. Fix failures, rerun those cases, then rerun the entire CORE suite even if no defect was found. A zero-defect iteration still needs new executed cases and the CORE rerun.
- Iteration 3 — COMBINATIONS AND RELEASE: derive NEW cross-feature/stateful cases, then de-duplicate and run them. Check sequences such as create/edit/cancel/retry, role handoffs, reload/restart, and repeated actions where relevant. Inspect target UI sizes, accessibility basics, copy, loading/empty/error states, logs, release artifacts, and the live deployment/provider result if required. Rerun the entire CORE suite, the accumulated automated regression suite, and every previously failed case. A zero-defect iteration still needs new executed cases and the CORE rerun.
- At the end of iteration 3, check the coverage floor and every Must criterion against QUALITY_CASES.md and the feature ledger. If a Must item or significant defect remains, run ONE focused iteration 4 with fresh cases around the defect, adjacent regressions, and a full CORE rerun; otherwise stop. After iteration 4, stop even if something remains and report it as blocked/unverified with evidence and exact next action. Never start iteration 5 or claim a case passed because it was planned. A PRD can demand stricter release gates than this default.
- In each iteration, choose the stack's real test tools: unit/integration tests, browser, emulator/device, API/database probes, deployment checks, or direct artifact inspection. Execute the case, capture a command/result or visible artifact, fix failures, and rerun the failed case and affected regressions. A generated test file, screenshot, or green build alone cannot prove an unexecuted case. Keep secrets and private data out of evidence.
- Keep PROGRESS.md short with `Iteration | new cases executed | failures fixed | CORE rerun result | open/blocked | next action`. Only mark an iteration complete after its NEW cases and the CORE suite ran. Keep detailed distinct cases in QUALITY_CASES.md and repeated CORE results in REGRESSION_RUNS.md. On continuation, read all three files and resume the current iteration at its next unrun case or CORE rerun. At the end of iteration 3 (or 4 if needed), run the kit's `CHECK_QUALITY_CASES.ps1 -Project <project-folder>` on this Windows PC. It mechanically checks distinct case counts, rounds, outcomes, evidence fields, and three runs of the SAME CORE case IDs; it cannot tell whether a result was fabricated or whether a PRD item was omitted, so manually compare the requirement IDs with the PRD too. If PowerShell is unavailable on another machine, perform the same checks with the project's native tools. A NOT READY result is a release blocker; fix it within the bounded loop or report exact blocked cases after the final iteration. The final report must give new-case counts and CORE rerun results per iteration, coverage gaps, and honest limits. Do not fabricate results to satisfy the count.
- Run relevant static checks, unit tests for business rules, integration tests for important boundaries, and end-to-end tests for Must flows. Choose test tools for the stack: browser for web, emulator/device for mobile, API/database tests for services, deployment checks for infrastructure. Do not run a web-only audit against a backend-only project.
- Verify the deployed version and its actual behavior when deployment is part of the PRD. A green build alone does not prove a user flow. If real-device or external-account testing is impossible, mark it blocked or unverified and state exactly what remains.
- Test failure paths and role/security boundaries. For paid integrations, use the appropriate sandbox or safe low-cost test according to the PRD. Do not create charges or send messages to third parties without authorization.
- When a check fails, investigate and fix it, then rerun that check. Record command, result, and meaningful limits. Never report a feature as verified from code inspection alone.
- Do not claim a WCAG level, contrast ratio, storage capacity, performance result, or provider limit without a measurement or current source. Report the behavior actually checked.
- Do not end a turn with only an Implementation Plan or a partially finished phase when the next authorized step is available. Continue through implementation, debugging, release checks, and deployment as the PRD requires; report results after the end-to-end work is done.
- Before publishing a repository or artifact, scan tracked files and git history for secrets and private data; inspect the release bundle. Do not make a private repository public without owner authorization. Follow explicit owner instructions about publication.

6. GIT, DEPLOYMENT, AND HANDOFF
- Use the owner's specified repo/host/account. When unspecified, ask only if ownership or publication cannot be safely inferred. Preserve existing branches and data; do not force-push or delete live resources without authorization.
- Keep credentials, signing keys, database URLs, local QA output, and personal files out of git. A repository may include PRD.md or design files when useful; there is no universal ban on agent-related filenames. Use .gitignore or local excludes as appropriate and scan the staged diff before pushing.
- Before deploying a static site, parse/lint every changed JavaScript and CSS file (a successful file copy or Wrangler upload is not a syntax check), inspect the IDE Problems list, and run a browser smoke test for the affected interaction. Recheck these after the last edit; release requires zero unresolved parse errors.
- Commit coherent changes with factual messages. No boastful claims. Deploy to the target named in the PRD, verify its URL/revision and core flows, and keep a rollback path when the change can disrupt users.
- If a GitHub workflow or deployment fails, use the `github-deploy-debug` skill: identify the exact commit and first causal error, fix that cause, then verify the run and live revision. Do not switch providers, disable tests, or blame cache without evidence.
- Report in plain language: what changed, where it is, how it was tested, what remains unverified, and any owner action that is truly required. Give numbered click-by-click instructions for manual account steps. Never claim production readiness for a prototype.
- A new provider is not ready just because a key exists. Verify the account/project, permissions, sender or domain, callback URL, secret placement, quotas/billing, runtime call, and user-visible result that apply to that provider. Mark each as verified, pending owner action, or blocked in PROGRESS.md.

7. WHEN INFORMATION IS MISSING
- Search the repo, docs, connected services, and current provider documentation first. Make small reversible implementation decisions yourself.
- Ask one concise question only if the answer changes the product, commits money, exposes private data, or is required for a blocked integration. Keep working on independent tasks while waiting.
- The owner can change the PRD during a project. Update PRD.md and the feature ledger to reflect the accepted change, then implement and test it. The new instruction wins over this playbook.
